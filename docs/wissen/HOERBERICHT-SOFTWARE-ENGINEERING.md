Matrixgame-Anwendung: Evolution Update 003b – Die Ingenieurskunst hinter dem Spiel. Jeder Abschnitt ist ein Vorlese-Häppchen, TTS-tauglich in web/hoerbericht-se.html. Geschwister-Bericht: HOERBERICHT-KI-VORLESUNGEN.md (Q83).

## KAPITEL 1: WAS IST SOFTWARE ENGINEERING?
Software ist nicht nur das Programm. Software ist das Programm plus Dokumentation, Konfigurationsdaten, Installation, Betrieb, Reparatur und Weiterentwicklung. Die Folien zeigen das ironisch: zuerst obfuskiierte C-Programme (ein springender Ball, ein Schachspiel in wenigen Zeilen, vom IOCCC – dem Wettbewerb für unlesbaren Code). Programmieren kann Kunst sein. Aber Software Engineering ist die systematische Ingenieursdisziplin, die man auf Software anwenden musste, nachdem die Softwarekrise der 60er zeigte: Budgetüberschreitungen, Zeitüberschreitungen, zu viele Fehler, unzureichende Sprachen, fehlende Methoden und Werkzeuge.

## KAPITEL 2: BESONDERHEITEN VON SOFTWARE
Software hat keine physischen Grenzen: Es gibt keine natürliche Trennung von Subsystemen, ein lokaler Fehler kann das ganze System betreffen. Software verschleißt nicht wie Hardware, aber sie muss sich ständig verändern, um neue Anforderungen und Umgebungen zu bedienen. Software lebt länger als geplant und ist schwer zu messen: Zeilen Code sind KEIN Qualitätsmaß. Berühmte Fehlschläge der Folien: London Ambulance Dispatch, Toll Collect, elektronische Gesundheitskarte. Ursachen: unklare oder widersprüchliche Spezifikation, wandelnde Anforderungen (moving target), fehlende Werkzeuge/Methoden/Weiterbildung, Management-Probleme. Kernsatz: „Ein Projekt fällt an ungedeckelten Spezifikationen" – die Software-Version der Untergangs-Kern-These.

## KAPITEL 3: VOM WASSERFALL ZU AGILEN PROZESSEN
Das Wasserfall-Modell (Anforderungen → Analyse → Design → Implementierung → Test → Wartung) ist elegant linear, aber ignoriert die Realität: Anforderungen sind zunächst unvollständig und ändern sich; Feedback kommt zu spät. Die Antwort seit 2001: das AGILE MANIFEST: Individuen und Interaktion über Prozesse und Werkzeuge; funktionierende Software über umfassende Dokumentation; Zusammenarbeit mit dem Kunden über Vertragsverhandlung; Reaktion auf Veränderung über das Befolgen eines Plans. EXTREME PROGRAMMING (XP) konkretisiert das: kleine Releases, Paarprogrammierung, Test-First, Refactoring, kontinuierliche Integration, Planung mit User Stories. Matrixgame: Unsere Arbeitsweise ist implizit XP: kleine Commits, immer verbesserter Stand, Refactoring als Routine (Unit-Fight V1 → V2!).

## KAPITEL 4: ANFORDERUNGSANALYSE (REQUIREMENTS ENGINEERING)
Der wichtigste Teil des Fachs für echte Projekte. Anforderungstypen: (1) USER-REQUIREMENTS: abstrakt, für Stakeholder. (2) SYSTEM-REQUIREMENTS: präzise, für Entwickler. (3) FUNKTIONAL: was soll das System tun. (4) NICHT-FUNKTIONAL: unter welchen Umständen gut genug (Performance, Sicherheit, Usability) – und NUR gültig, wenn sie messbar/verifizierbar formuliert sind. (5) DOMAIN: Fachliches aus der Domäne. Wichtig: Mehrdeutigkeit und verdeckte Annahmen sind die Quelle der meisten Fehler. RE-Prozess: Machbarkeitsstudie, Elicitation, Specification (SRS-Dokument), Validation. Die Folien illustrieren mit Idealbeispielen ("Schuhe müssen getragen werden" – von wem, wo?): Sprache ohne Protokoll produziert Missverständnisse. Matrixgame: Offen gebliebene Fragen werden dokumentiert und versioniert – nie still entschieden.

## KAPITEL 5: USE CASES UND DOMÄNENMODELL
Use Cases beschreiben Interaktion zwischen Akteuren und System als Szenarien: MAIN SUCCESS SCENARIO plus Extensions (alle Was-wäre-wenn-Pfade), im "fully dressed"-Format mit Stakeholdern, Vorbedingungen, Hauptfluss, Erweiterungen. Danach das DOMÄNENMODELL: das Fachvokabular als konzeptuelles Klassendiagramm. Werkzeug: NOUN ANALYSIS – Substantive aus dem Problemtext sammeln, schlechte rauswerfen (Berichte, Redundanzen), gute behalten; prüfen: Klasse oder Attribut? Attribut oder Assoziation? Das Domänenmodell beschreibt die Welt der Fachbegriffe, NICHT technische Details (keine UI-, keine DB-Klassen). CRC-KARTEN (Class–Responsibility–Collaborator): Karteikarten mit Verantwortlichkeiten und Kooperationspartnern, die im Team-Improvisationsspiel entstehen – der Niederschwelligkeitseinstieg in Design.

## KAPITEL 6: UML: VIER DIAGRAMMTYPEN
Professionell genutzt: USE CASE DIAGRAM (Actors, Use Cases, include/extends – billig aber UNSCHARF, nicht zu tief ausbauen), CLASS DIAGRAM (Klassen, Assoziationen, Generalisierung), SEQUENCE DIAGRAM (Zeitachse, Lifelines, Messages, Interaktionsframe, Loop/Opt/Alt – der direkteste Weg: "Wer ruft wen mit was in welcher Reihenfolge?"), STATE MACHINE (Zustände, Übergänge, Events, Composite States). Besonders stark: SYSTEM SEQUENCE DIAGRAMS mit SYSTEM OPERATION CONTRACTS: vor und nach jedem Systemaufruf wird der Zustand exakt notiert (Vorbedingungen, Nachbedingungen). Das ist DESIGN-BY-CONTRACT – der Vorlesungs-Bruder unserer Guardian-Clamps und isValid-Prüfung im Genesis-Core (Q18).

## KAPITEL 7: SOFTWARE-QUALITÄT
Externe Qualität spürt der NUTZER: Korrektheit, Robustheit, Erweiterbarkeit, Sicherheit, Bedienbarkeit (inkl. Folien-Demos verwirrender GUIs). Interne Qualität spürt der ENTWICKLER: Lesbarkeit, Wartbarkeit, Testbarkeit, Struktur. Interne Qualität ist der Puffer für externe: Wer sie opfert, verliert langfristig beides (technische Schulden). Werkzeuge: METRIKEN (zyklomatische Komplexität = Zahl der unabhängigen Pfade; LCOM als Kohäsionsmaß), STatische ANALYSE (FindBugs – Bug-Patterns; SLAM/SDV-Verifikation von Microsoft), INSPEKTIONEN (Reviews im Team), FORMALE VERIFIKATION (Design-by-Contract, Laufzeit-Assertions). Code Reviews sind die höchste Rendite pro Zeiteinheit: „Vier Augen sehen mehr als zwei" – das Perspektiven-Ensemble (Q63) in Software-Farben.

## KAPITEL 8: TESTING UND JUNIT
Testing ist systematisch, kein Zufalls-Fummeln: TESTPLAN, TESTDRIVER, TEST SUITES, AUTOMATISIERUNG mit JUnit. Coverage-Kategorien, strenger werdend: Statement Coverage, Basic Block, BRANCH Coverage, PATH Coverage, und LOGIC COVERAGE: Condition, Decision und schließlich MODIFIED CONDITION DECISION COVERAGE (MC/DC) – der Standard der Luftfahrt. Wichtige Lektionen: 100 % Statement Coverage beweist NICHTS über korrekte Ergebnisse (sie zeigt nur, dass Zeilen LIEFEN); Tests brauchen erwartete Ergebnisse als Test-Oracle. Und die Dijkstra-Regel: Testing zeigt die ANWESENHEIT von Fehlern, niemals deren Abwesenheit. Deshalb bleibt ein nicht kompilierter Kern Evidenzklasse C, bis der echte Compile (Q29/Q57!) ihn zur Klasse A macht: Der Vorlesungs-TEST-Loop IST unsere Compile-Queue.

## KAPITEL 9: VERANTWORTUNG, COUPLING UND COHESION
Das Herz der Objektorientierung: RESPONSIBILITY-ASSIGNMENT. Pro Operation fragt man: „Welches Objekt weiß das? Wer sollte es tun?" Die zwei Fehlerarten: (a) TIGHT COUPLING: Jede Klasse kennt jede, eine Änderung dominiert alle. (b) LOW COHESION: Eine Klasse hat wirre unverbundene Aufgaben – die "God Class". Messgrößen: Coupling (Beziehungen zwischen Klassen), LCOM (Lack of Cohesion of Methods). Zentrales Prinzip: SINGLE RESPONSIBILITY PRINCIPLE (SRP): Eine Klasse hat EINE Verantwortung und damit genau einen Grund zur Änderung (Folien-Beispiel: Rectangle zerlegt in geometrische und GUI-Verantwortung). Matrixgame: Unsere Wächter-Suiten (v1.0–v2.7) sind SRP: Jeder Wächter hat genau eine Aufgabe – deshalb können sie wachsen, ohne eine Archiv-God-Class zu werden.

## KAPITEL 10: STRATEGY PATTERN
STRATEGY: Definiere eine Familie von Algorithmen, kapsle jeden einzeln, mache sie austauschbar. Statt Unterklassen zu bilden, hält ein Objekt eine Referenz auf eine austauschbare Strategie hinter einem Interface. Merksatz: „Programmiere gegen ein Interface, nicht gegen eine Implementierung" (GRASP-Polymorphismus). Beispiele der Folien: Layout-Manager, Kompressionsstrategien, Java Swing. Matrixgame: Das Verhalten-Interface im Unit-Fight V2 (Königsjäger, Leibwacht, Artillerie, Nadel, Heiler) IST das Strategy Pattern – die Vorlesung benennt die Struktur, die wir bereits gebaut haben, im Wortschatz der Industrie.

## KAPITEL 11: OBSERVER UND MVC
OBSERVER: Ein Subjekt hält eine Liste von Beobachtern und verteilt Updates an alle Angemeldeten. Ziel: KOMMUNIKATION OHNE COUPLING. Zwei Modi: PUSH (Subjekt schickt Daten mit) und PULL (Beobachter holt nur, was er braucht – flexibler). Observer ist die BASIS für MVC (Model-View-Controller): States getrennt von Darstellung und Steuerung; Views registrieren sich als Observer am Model (Folien-Beispiel: Counter mit Buttons). Matrixgame: UNSERE BROADCAST-Architektur (Avatar Broadcast, Update 002) IST Observer: Das KNOWLEDGE NODE ist das Subjekt, die Avatare sind Beobachter, und die Privacy-Policy entscheidet, WER welche Updates empfängt. Die 6-Prüffragen des Broadcasts sind der PUSH/PULL-Designentscheid.

## KAPITEL 12: FACTORY UND COMPOSITE
FACTORY METHOD: Eine Oberklasse definiert, WIE Objekte erzeugt werden; Unterklassen entscheiden, welches konkrete Objekt entsteht (Folien-Beispiel: Dokumenten-Framework, das PDF und SVG speichern soll, ohne an ein Format gebunden zu sein). ABSTRACT FACTORY: Eine Fabrik erzeugt verwandte OBJEKTFAMILIEN, die zusammenpassen (z. B. UI-Fabrik pro Betriebssystem). Kernsatz: „Supporting VARIETY by COMMON INTERFACE": Vielfalt durch gemeinsame Schnittstelle, nicht durch if-else-Lawinen. COMPOSITE: Einzelobjekte und Zusammensetzungen werden gleich behandelt – die Figure aus der Anfangsvorlesung besteht aus Shape-Objekten (Quadrate, Dreiecke, Kreise, Text). Matrixgame: Die Wächter-Suiten sind eine Fabrik gleich behandelbarer Prüfmodule, die Perception-Schichten sind Composite (eine Wahrnehmung aus vielen Sensorbausteinen).

## KAPITEL 13: DIE GROSSE SYNTHESSE: INGENIEURSKUNST UND MATRIXGAME
Damit schließt der Hörbericht. Die Software-Engineering-Vorlesungen geben uns die INGENIEURSDISZIPLIN, die KI-Vorlesungen (Q83) die MATHEMATIK, und das Matrixgame gibt die ARCHITEKTUR. Die Doppelbrücke ist geschlossen: (1) Softwarekrise 60er = Untergangs-Kern (Q38): Projekte fallen an ungedeckelten Bilanzen und unklaren Spezifikationen. (2) Requirements-Analyse = Wahrnehmungs-Protokoll: Ambiguität ist ein Konfabulations-Detektor-Trigger. (3) Design-by-Contract = Wächter-Clamps + isValid. (4) Code Review = Perspektiven-Ensemble (Q63 Ensemble-Loop). (5) SRP = jeder Wächter genau eine Aufgabe. (6) Observer = Avatar Broadcast. (7) XP/kontinuierliche Integration = unsere Compile-Queue Q57/Q83/K-8. Kernsatz der Vorlesung: „The one software process does not exist" – verschiedene Systeme brauchen verschiedene Prozesse. Das gilt für KI und für Kollektive identisch.
